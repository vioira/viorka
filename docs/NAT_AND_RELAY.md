# NAT VPS、端口映射和链路编排

## 1. 为什么 NAT 资源不是布尔值

NAT VPS 可能提供：共享公网 IP、服务商分配的有限公网 TCP 端口、独立内网 IP、受限 UDP、无 QUIC、对外 TCP 连接数限制、IPv6 可直连等。它们是多个能力，不应用 `is_nat` 一项推断。

Viorka 使用三组数据描述：

- `NodeAddress`：公网/内网 IPv4、IPv6、域名，可有多个地址。
- `PortAllocation`：公网 Host:Port 与内网 Host:Port 的 TCP/UDP 映射。
- `NodeCapabilities`（M1 待建）：UDP 是否可用、支持的系统进程管理器、TCP 资源限制、可用引擎、网络功能。

## 2. 端口映射示例

```yaml
# 文档样例，并非当前可导入配置
node: nat-jp-01
addresses:
  private_ipv4: 10.0.0.2
port_allocations:
  - public_host: 203.0.113.10
    public_port: 30001
    private_host: 10.0.0.2
    private_port: 10001
    transport: tcp
    owner: provider
    provider_name: example-provider
```

上面 `203.0.113.10` 为文档示例地址，**不是可用服务器**。用户在面板创建 `10001/TCP` 代理服务时，应使用内网监听 `10001`，对外订阅才使用 `203.0.113.10:30001`。

节点详情页新增服务时，对外入口默认填入节点上报的公网 IPv4（缺失时使用 IPv6）和服务监听端口；节点尚未上报 IP 时保持入口为空。新增期间入口端口随协议配置和服务端口变化，手动修改入口端口后停止跟随。编辑已有服务保留已保存的入口。默认值不代表公网连通性已验证，NAT 节点仍须按实际映射修改地址和端口。

新增 sing-box 服务的监听 IP 默认为 `::`，用于同时接收 IPv4 和 IPv6 连接；其他引擎仍默认为 `0.0.0.0`。监听 IP 可手动修改，已有服务不自动变更。

**映射归属决定操作权限**：

| 归属 | 管理方式 |
|---|---|
| `provider` | 服务商配置；Agent 只能发现/验证，不能擅自增删公网端口 |
| `node` | 用户有 root/network 权限时可通过受控 nftables/iptables 适配器管理 |
| `manual` | 用户手工维护端口对照，Viorka 只读或要求确认后更改 |

## 3. 端口能力检查

发布前应执行：

1. 协议是否支持：节点允许 TCP、UDP 或两者。
2. 公网映射与内网监听端口映射是否匹配。
3. 本地监听端口是否冲突：按 namespace、IP、端口、TCP/UDP 判断。
4. 远端是否确实可达：通过可信探测端执行连接性检查；单纯 `ss -lnt` 不能证明公网映射生效。
5. 如果服务商标称 TCP 并发有限制，不应自动配置大量短连接或强制启用 QUIC。

## 4. 中转链路

示例：

```mermaid
flowchart LR
  Client[客户端\nMihomo / Loon] -->|TCP| Relay[香港 VPS\nRealm TCP Relay]
  Relay -->|TCP| Map[日本 NAT VPS\n公网分配端口]
  Map -->|DNAT| Target[日本 NAT 内网\nXray VLESS + REALITY]
```

### 编排对象

- 入口：哪一节点对客户端暴露 Host/Port；是否通过 NAT 或域名。
- 中转：Realm rule 监听 IP/端口、转发目的端 Host/Port、TCP/UDP 允许性。
- 出口：最终 Xray/sing-box 节点与其内网监听。
- 依赖：先确保出口服务健康，再发布中转，最后更新订阅/展示入口。

### 约束

- TCP 透明转发不应该修改 Reality/TLS payload，`server_name`/public key/short_id 等仍以最终出口引擎为准。
- Relay 不需要持有出口端身份私钥；不要把出口 REALITY 私钥复制给 Relay。
- 使用 NAT 时公私端口可能不同，不可将外网端口直接当目标主机监听端口。
- 对 UDP 受限节点，链路拓扑应显示不可用而不是默默降级为可用。
- 对于端口中转循环（A→B→A）应阻止发布并提示循环路径。

## 5. 资源拓扑与 UI（规划）

初始资源图：`Node → Engine → Service → PortAllocation`；M3 新增 `RelayRule(from,to)`。UI 要支持：节点资源列表、地图/拓扑、端口映射表、入口出口角色、连通性探测结果（带测试时间戳）。

## 6. 多跳配置可靠性（规划）

1. Orchestrator 计算资源依赖图，检测循环和端口冲突。
2. 按“出口先、入口后”的顺序生成一组 deployment tasks。
3. 每一步有 Revision、幂等键和健康检查，失败后执行有界补偿。
4. 对端口失联、服务商端口变化、节点离线明确告警；不要静默重写业务配置。

## 7. 后续 Provider Adapter

未来可扩展服务商端口映射 API、云防火墙规则和 NAT 对外地址发现。但必须先界定 Provider Credential 的保存、权限最小化和错误回滚，否则默认保持**手工录入/只读同步**。

## 托管 Realm 单跳线路

1. 在「代理 → 中转线路」选择「创建中转线路」，也可从节点 Realm 面板预选入口，或从落地服务详情选择「添加中转」预选服务。选择可管理的托管 Realm，并填写客户端使用的公网入口。地址优先采用入口节点上报的公网 IPv4，其次是 IPv6。地址缺失时手动填写。
2. 公网端口初始为 `10080`，本机默认监听同一端口，入口节点上报地址为 IPv6 时监听 `::`，其他情况监听 `0.0.0.0`。NAT 公私端口不同时展开「本机监听与 NAT 映射」并填写内网端口。已登记的服务商映射可以匹配同节点、同端口且覆盖目标内网地址的通配监听。
3. 选择落地服务。候选来自有导出权限、已发布并确认运行的 VLESS TCP REALITY 服务。拨号使用该服务的对外地址与端口，页面同时显示落地监听地址以便核对。
4. 「仅保存草稿」保留编辑进度。「保存并审查发布」保存后直接打开确认页，列出入口、拨号目标和同实例其他中转线路。取消发布会保留草稿。启动意愿为停止或实例尚未运行时，确认操作为「启动 Realm 并发布」，影响整个实例。
5. 发布时核对线路草稿版本、审查时的 Realm 修订、普通草稿版本和启动状态。审查过期时可重新读取并确认，无需重新保存线路。落地连接发生变化时须重新编辑确认。Realm 确认应用并运行后，Panel 自动检测已发布快照中的客户端公网 TCP 入口。检测通过后，线路才可供订阅选择。原样保存会保留草稿版本，已生效的同一版本保留公网验证结果。


| 操作或观测 | 订阅下次拉取时的行为 |
| --- | --- |
| 新草稿或仅编辑已有草稿 | 新线路尚不可选。已有线路继续使用上次确认的发布版本。 |
| 发布新的实例目标 | 暂停该线路输出，等待匹配修订的应用回报、本地监听和拨号检查，以及该修订的公网验证。 |
| 已确认运行，公网验证通过 | 输出入口公网地址以及落地服务的 REALITY 参数。 |
| 入口 Agent 的单次周期拨号超时、观测过期或管理连接离线 | 保留此前确认且配置仍匹配的版本。页面显示时间、失败阶段或离线状态。公网记录超过 24 小时标记为过期。 |
| 公网重新检测 | 提交后立即暂停分发。检测失败或探测点不可用时继续排除，新的成功结果可恢复输出。 |
| 同端口换落地后发布失败 | 仅当入口仍报告运行、失败类型可证明旧配置保留或已回滚，且公网映射、监听、旧规则、落地连接指纹及旧验证均匹配时恢复旧版输出。 |
| 停用、落地连接变更、运行状态无法核对 | 排除该中转入口。停用在事务中提交撤除任务，节点可在重连后执行。节点确认撤除后方可删除已发布线路。 |
| 备份恢复 | 吊销旧链接，按既有实例恢复流程核对，保留历史记录。匹配的入口和落地恢复核对完成后自动重测，只有本次恢复之后的成功结果可以恢复线路资格。 |

入口管理与落地导出授权分别校验。入口管理员失去落地导出授权后，仍可停用并撤除原有规则。订阅按所有者当前权限检查入口与落地，已选项失去导出权限会使整份拉取失败。直连与中转使用独立的稳定引用，原有直连订阅保留原身份和顺序。

### 接口与探测

`GET /api/v1/relay-landings` 按授权和运行状态筛选落地服务，支持搜索与游标分页。`GET /api/v1/relay-entries` 返回可管理的入口及节点上报的公网地址。管理端使用 `/api/v1/relays` 查询、保存草稿和删除线路。`publish`、`withdraw`、`probe` 返回 202 和持久任务。`POST /api/v1/relays/{id}/public-probe` 接受当前发布 `revision` 和最新 `check_id`，返回 202 和持久化检测状态。请求中没有可指定地址或端口的字段。字段及筛选见 [OpenAPI](../api/openapi/openapi.yaml)。

入口 Agent 在协商 `engine.relay.probe.v1` 后可执行只读重测。任务指定受管规则 ID 与已应用实例修订。检测命令的修订号仅用于任务派发和回报校验；手动或定时重测都不创建配置修订，也不递增引擎或线路的目标版本。Agent 对照本机托管配置，分别报告监听和目标 TCP 连接结果。同实例执行串行，手动重测冷却 60 秒。定时器每分钟选择至多 8 条线路，单条间隔至少 30 分钟。没有该可选能力的 Agent 不接收重测任务。

公网 TCP 检测由 Panel 单独调度。发布事务保留端点与待检任务，只有对应 Realm 成功应用并报告运行后才领取。每次领取或写入结果时重新检查授权与线路状态。重测、切换修订、停用及备份恢复都会隔离旧结果；进程中断后，30 秒租约过期即可重新领取。详情返回 `public_probe` 中的端点、发布修订、状态、来源、失败原因、完成时间及成功连接的 IP。

公网探测视角在部署时选择。Panel 与入口处在同一内网或 NAT 后面时，可通过授权外部节点发起 TCP 连接。网络位置未知、地址归属无法核对或未取得成功回报时，订阅保持暂停。部署参数和授权边界见[公网探测点配置](DEPLOYMENT.md#中转线路公网探测点)。

### 验收与回退

发布请求携带线路草稿版本、幂等键及线路详情中的 `publish_base`（通过请求字段 `review` 传回）。任务受理返回 202。确认成功、外部实测和订阅输出分别检查。

版本上线前需要在两台授权 NAT 节点上核对四个端点，导入测试订阅、完成 REALITY 握手与实际请求，并保存正常、错映射、落地拒绝、同端口切换、回滚和离线撤除记录。记录中应包含客户端和引擎版本、任务与修订、验证来源、时间及落地侧证据。

回退前核对持久任务与已运行规则。回退数据库应使用发布前的一致性备份，恢复后重新核对节点和链接。P1 的有序组、远程源和逐入站独立凭据另行交付。
